# الاختبارات وCI

شغّل أصغر مجموعة فحوص مناسبة للتغيير ثم وسّعها حسب الوقت والمخاطر. اذكر فقط ما شغّلته فعلياً.

## أنواع الفحوص
1. اختبارات الوحدة لقواعد الأعمال والحسابات.
2. اختبارات التكامل لقواعد البيانات وواجهات API والخدمات.
3. اختبارات المسارات الأساسية من البداية للنهاية.
4. lint وفحص الأنواع والتحليل الأمني.

اختبر النجاح والفشل والحالات الطرفية والصلاحيات ذات الصلة. لا تضف اختبارات شكلية لا تتحقق من سلوك مهم.

## Python
افحص المشروع أولاً واستخدم الأدوات الموجودة. أمثلة شائعة وليست إلزامية:
```bash
pytest
pytest --cov
ruff check .
ruff format --check .
mypy .
bandit -r .
```
لا تفترض وجود مجلد `src` أو إعدادات تغطية أو mypy قبل التحقق.

## JavaScript/TypeScript
افحص `package.json` أولاً؛ قد تتوفر scripts مثل:
```bash
npm test
npm run lint
npm run typecheck
npm audit
```
لا تفترض أن هذه scripts موجودة.

## فحوص هذا المستودع (موجودة فعلاً)
```bash
uv run --with pyyaml python tests/test_apply.py     # اختبارات apply.py — بلا شبكة
bash scripts/check-workflows-sync.sh                # workflows/ == .github/workflows/
uv run --with pyyaml python scripts/check-action-pins.py # مراجع Actions الخارجية المباشرة مثبتة
bash scripts/check-tool-versions.sh                 # إصدارات الأدوات داخل shell تطابق scripts/tool-versions.cfg
```

## GitHub Actions
- استخدم أقل صلاحيات لازمة، وأسماء checks ثابتة.
- شغّل الاختبارات على Pull Requests والفرع الافتراضي.
- لا تضع أسراراً في workflow ولا تمرر مدخلات غير موثوقة إلى shell مباشرة.
- راجع إصدارات Actions وتحديثاتها؛ الوسوم أسهل في التحديث لكنها ليست تثبيتاً غير قابل للتغيير مثل SHA.
- قواعد حماية الفرع يجب أن تشير إلى check يظهر فعلاً في CI، وأن تكون القائمة الحية مطابقة لما تنص عليه السياسة.
- في هذا المستودع اسم فحص الاختبارات والاتساق هو `Regression and consistency checks` (اسم الـ job)، بينما فحصا الأسرار والتحليل هما `gitleaks` و`semgrep`. بعد التحقق من هذه الأسماء في PR، يجب أن تكون الثلاثة مطلوبة في ruleset `main`.
- تمرير `--check` إلى `apply.py` يستبدل قائمة الفحوص المطلوبة كاملة؛ اذكر كل الفحوص المطلوبة في الأمر. بعد التطبيق، افحص ruleset الحي يدوياً لأن نجاح CI لا يثبت أن قواعد الحماية تضبط هذه الفحوص.

## اختبارات حدود الأمان في apply.py
تتضمن اختبارات الوحدة حالات لرفض أسماء المستودعات غير الصالحة، وللتأكد من أن `--dry-run` لا يسمح بطرق HTTP غير معروفة أو بخيار `-X` ناقص. هذه الاختبارات محلية/معزولة ولا تتصل بـ GitHub؛ تشغيلها في Actions يتحقق من السلوك البرمجي ولا يثبت وحده صحة rulesets الحية.

## التقرير
ميّز بوضوح بين: نجح، فشل، لم يُشغّل، وغير منطبق. إذا تعذّر الاختبار بسبب بيئة أو اعتماديات، اذكر السبب ولا تصف المهمة بأنها مختبرة بالكامل. التغطية لا تساوي جودة الاختبارات.
